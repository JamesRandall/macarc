# Reference audit

`references/` is read-only reference material. No code from it is compiled into MacArch.

| Project | Revision | Licence | How it was used |
| --- | --- | --- | --- |
| Eichhörnchen (`references/Eichhoernchen`) | 3303ac6 (2026-01-25) | MIT (© 2024-2026 RichardBrown384) | Primary behavioural reference for the A3000 hardware: MEMC CAM/PPN decode, IOC register map and bank decode, KART keyboard protocol, VIDC register formulas, PCF8583/I2C, WD1772 command flow, key matrix codes. All Swift code is written independently, but the hardware decomposition follows it closely. That is compatible with any licence, provided the MIT notice is credited if any portion is ever derived more directly. |
| Arculator (`references/arculator`) | 532e8f3 (2026-10-11) | GPLv2 (`COPYING`); the upstream README also restricts AI-generated contributions | Read only to confirm specific behaviour: video DMA `Vend` is inclusive, the sound period is `SFR+2` µs, IOC timer period is latch+1, the 32 KB CAM decode, and memory/IOC cycle costs. For the machine models: the CP15 register numbers and ARM3 identity word; the slave-MEMC page bits (CAM address bits 7 and 12); and Acorn's wiring of the 400-series ST506 controller (IOC bank 5 offsets, DREQ into IRQ B bit 3, DACK data addresses, drives as units 1 and 2, little-endian sector data). For the A5000 family: the 82C711 port map and configuration keys, the IOEB registers (device ID, monitor ID, clock select), the floppy DACK range with terminal count at &302A000, and the interrupt lines (floppy INT on IRQ B bit 4, index on IRQ A bit 2, DRQ on FIQ bit 0, IDE on IRQ B bit 3). The 765 and ATA command behaviour comes from their public specifications; the behaviour RISC OS depends on (terminal count between sectors, index pulses, data-rate probing) was found by tracing RISC OS itself. The chip behaviour itself comes from manufacturer and RISC OS documentation. No code was copied or translated. |
| MacBeeb (`~/code/macbeeb`, outside the repo) | 3b9cd6b; 370a026 for the debugger and MCP | GPLv3, the same owner as MacArch; its `Renderer.swift` credits b2 (GPLv3) | Model for the app's design: menu layout and shortcuts, customisable toolbar and lights, a per-window `@Observable` controller reached through `@FocusedValue`, the settings window, the rewind sheet, display styles and zoom. Also for the debugger and MCP server: the debugger window's layout and shortcuts, the breakpoint model (kinds, conditions, hit counts, log points), the expression syntax, step back and reverse continue over rewind history, the profiler views, the MCP tool names and descriptions, attach mode over a socket, the hold between calls, and the MCP menu's setup and activity log windows; the debug adapter (requests, capabilities, polling for stops, source breakpoints) and the VS Code extension's shape (package.json contributions, launch through a DebugAdapterServer, starting the app). The ARM assembler is MacArch's own (MacBeeb runs BeebAsm, a GPL C++ program, which MacArch doesn't use): its syntax follows BBC BASIC V's assembler and the encodings come from the ARM2/ARM3 instruction set as documented by Acorn and ARM, checked against MacArch's own disassembler. The Archimedes-specific parts (ARM modes and banked registers, SWI names, idle detection, screen text from the system font) are MacArch's own. The Swift was written afresh for MacArch rather than copied, but several files follow MacBeeb's structure closely (toolbar, rewind sheet, keyboard settings, renderer shader approach). If MacArch is released under a licence other than GPLv3, the owner should confirm that is acceptable for this derived design. |

| ArcEm (`references/ArcEm`) | b682d4b (2026-09-23) | GPLv2 (`docs/COPYING`), ARMulator-derived | Read only to confirm one fact: which physical address bits MEMC routes to DRAM row 8 and 9 and column 2, 3 and 9 at each page size (`ARMul_ManglePhysAddr`'s comment and switch). `MEMC.dramOffset` is written independently as a lookup table; no code was copied or translated. |
| HxC Floppy Emulator HFE format (HxC2001's published file layout) | version 1 | Format documentation | `HFEImage.swift` is written from the published header, track list and side-interleaved cell layout; the MFM sync and address-mark decoding follows the IBM/ISO double-density format the WD1772 datasheet describes. | ZIP (PKWARE APPNOTE) and the Acorn ("ARC0") extra field | — | Format documentation | `ZipArchive.swift`: the end record, central and local headers, and the RISC OS extra field (load, execution address and attributes) that SparkFS and other RISC OS zip tools write. Deflate uses the system zlib. |
